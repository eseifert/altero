# Real identity-provider tests

Form parsing and the disposable live altero server are shared by the provider
test modules through `tests/idp/http.py`.

`test_keycloak.py` and `test_keycloak_protocol.py` run OIDC authorization-code + S256 PKCE and SAML
HTTP-Redirect/HTTP-POST sign-in against Keycloak 26.8.1, pinned by image digest
in `compose.yml`. Start it with the commands in
[Contributing](../../CONTRIBUTING.md#getting-set-up). The service imports
`altero-realm.json` at startup using Keycloak's
[realm import](https://www.keycloak.org/server/importExport) mechanism.

The realm is a disposable fixture, not deployment configuration. It disables
the TLS requirement for loopback HTTP and contains a public client secret and
user password. It has no persistent volume, no host-wide network binding and
no bootstrap administrator. A fixture service account has administration rights
only in the disposable `altero` realm, using a public test secret, so scenarios
can remove and restore actual group membership. Signing keys are generated by Keycloak; tests read
the signing certificate from its SAML metadata rather than committing a private
key. OIDC requires a confidential client and S256; the SAML client accepts
unsigned requests and emits signed, unencrypted assertions with persistent
NameIDs. Callback URLs are registered exactly for `http://127.0.0.1:18765`.

Each parametrized test starts a real uvicorn server and configures its provider
through the administrator HTTP endpoints. It follows the redirect, parses and
submits Keycloak's actual password form, then completes the code callback or
SAML form POST. No HTTP transport or assertion verifier is substituted. It
checks account creation, a second sign-in to the same local identity, browser
session creation, authenticated library access, local sign-out and refusal of
the browser cookie at the v3 API. The SAML POST deliberately carries no cookies,
as a cross-site POST with SameSite=Lax would, retaining the browser's cookie jar
for subsequent same-site requests.

Account-policy scenarios run through both protocols. Disabling provisioning or
requiring a group the user lacks refuses sign-in without creating an account.
The deprovisioning scenario first signs in a member of `researchers`, issues a
working API key, removes that membership through Keycloak's real Admin REST API,
then signs in again. It checks account suspension, refusal of existing browser
and API credentials, and actual key deletion when `revokeKeysOnLoss` is enabled.
With revocation disabled, the key is retained but blocked during suspension.
Restoring membership alone cannot reactivate the account: an administrator must
reinstate it, after which a retained key works and a revoked one still fails.
Each mutation of group membership is restored in `finally`; run serially.
The OIDC group mapper puts the claim only in UserInfo, exercising that real
back channel; SAML carries it in the signed assertion. Mapper configuration
follows the pinned Keycloak
[OIDC](https://github.com/keycloak/keycloak/blob/26.8.1/services/src/main/java/org/keycloak/protocol/oidc/mappers/GroupMembershipMapper.java)
and [SAML](https://github.com/keycloak/keycloak/blob/26.8.1/services/src/main/java/org/keycloak/protocol/saml/mappers/GroupMembershipMapper.java)
implementations.

This is an HTTP integration test, not a JavaScript browser test: it does not
prove browser cookie policy, the sign-in page's rendering or cross-site account
linking. Requests use a Safari User-Agent so Keycloak issues cookies usable on
HTTP loopback by Python's cookie jar. This follows Keycloak's
[SecureContextResolver](https://github.com/keycloak/keycloak/blob/26.8.1/services/src/main/java/org/keycloak/utils/SecureContextResolver.java)
Safari branch; the harness does not alter cookies or bypass a cookie policy,
and it establishes no Safari or macOS browser coverage.
Account linking and reauthentication also run through both protocols with
provisioning disabled. They check that the local account is retained, a later
directory sign-in reaches it, and fresh identity proof permits API-key issuance.
The SAML ACS POST carries no existing cookie; its verified continuation is
completed by a GET with the browser's retained jar. Focused handoff tests cover
expiry, replay, missing/wrong sessions, disabled/mismatched providers and misuse
at the original callbacks.

Local validation on 2026-10-31 also drove Chromium through a genuinely cross-site
flow (`localhost` for Keycloak, `127.0.0.1` for altero). Linking, ordinary sign-in
and reauthentication sent no cookies on their SAML POSTs; linking retained the
local account and reauthentication enabled key issuance. This browser check was
run locally, separately from the HTTP tests required in CI.

Protocol tests replay the actual OIDC code callback and signed SAML response
after local logout and require refusal without a new session. The SAML rollover
test creates a higher-priority RSA signing-key provider through Keycloak's
[Admin REST API](https://www.keycloak.org/docs-api/26.8.1/rest-api/index.html).
It observes the active key change, refuses its signature with only the old
certificate, accepts both PEM orders, restores the previous signing key, then
checks that removing its certificate removes trust. The extra key provider is
removed in `finally`.

Validity-window tests use unmodified Keycloak assertions and tokens, adjusting
only altero's validator clock to four or six minutes before the actual
`NotBefore`/`iat` or after `NotOnOrAfter`/`exp`. The four-minute offsets are
accepted; the six-minute offsets are refused without provisioning an account.
This tests the configured five-minute tolerance over the real exchange, not
clock synchronization between machines or Keycloak's own clock-skew policy.
The replay case checks the endpoint's combined single-use protections; the
independent assertion-ID replay table has its own unit and concurrency tests.

`test_simplesamlphp.py` supplies a second real SAML implementation. Its fixture
builds the upstream SimpleSAMLphp 2.5.3.1 full archive (including its dependencies
and built assets) from an exact URL and SHA-256, on the official PHP 8.4.27 CLI
image pinned by digest. No Composer install runs at build or startup. The
configuration follows the upstream
[IdP quickstart](https://simplesamlphp.org/docs/stable/simplesamlphp-idp) and
[metadata reference](https://simplesamlphp.org/docs/stable/simplesamlphp-reference-idp-hosted).
It generates a disposable signing key at startup, publishes the certificate
through SAML metadata, uses persistent NameIDs derived from `uid`, and signs
both response and assertion. The PHP development server is exposed only on
loopback at `http://localhost:18081`; this is test configuration, not a production
deployment recipe.

PHP 8.4.27 contains the 21 October 2026 fixes for
[CVE-2026-109618](https://github.com/php/php-src/security/advisories/GHSA-w8hw-w9fx-j79w)
and [CVE-2026-109619](https://github.com/php/php-src/security/advisories/GHSA-6wmf-4rv5-p3rp).
The image also disables `session.upload_progress.enabled` in its startup INI
for PHP's [23 October follow-up](https://www.php.net/archive/2026.php)
on CVE-2026-115560. Build/start checks require PHP 8.4.27, and the readiness
endpoint plus every live-test fixture check the actual runtime version and
that setting. These are checks of the pinned fixed release and configuration,
not exploit tests or a claim that all PHP dependencies have no vulnerabilities.

The SimpleSAMLphp cases submit its real password form and check stable identity,
multi-valued required groups, disabled provisioning, linking, ForceAuthn with
an existing IdP session, reauthentication for API-key issuance, callback replay,
tampered signed claims, and mismatched signing certificates/issuers. Both XML
signatures and persistent NameID format are asserted on actual responses.
Assertions are posted without cookies and handoff GETs use the retained jar.
The fixture's `localhost` IdP and `127.0.0.1` altero are different sites; HTTP
tests still do not enforce browser cookie policy themselves. Configurations
that encrypt assertions, use artifact binding or require signed AuthnRequests
are outside this fixture.

Local Chromium validation on 2026-10-31 also passed linking, sign-in and forced
reauthentication against SimpleSAMLphp across those two sites. All three actual
ACS POSTs omitted cookies; the verified handoff retained the local account and
fresh proof enabled API-key issuance. This browser run is separate from the
HTTP cases required in CI.

OpenID-provider conformance needs separate evidence.
The existing mock-based identity and SAML unit suites remain useful for precise
negative cases; they do not replace this test.

An unset `ALTERO_TEST_KEYCLOAK_URL` or `ALTERO_TEST_SIMPLESAMLPHP_URL` skips that
provider's cases locally. A configured but unreachable service fails. CI starts
the same Compose services, sets both URLs and
rejects skips. Inspect a failed service with:

```sh
docker compose -p altero-idp-tests -f tests/idp/compose.yml logs --no-color
```
